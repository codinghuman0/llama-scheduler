# Ryzen 5 5500U에서 공용 실험 스크립트로 재측정한 결과

2026-11-25, AC 전원을 연결한 AMD Ryzen 5 5500U에서 공용 `placement`를 실행했다. **서로 다른 8개 요청의 전체 생성 처리량은 `prefill-pcore`가 기본 Linux 대비 평상시 −0.58%, `cpu25`에서 −0.63%였다.** 두 조건 모두 95% 구간에 0%가 포함됐다. 앞선 AMD 캠페인의 같은 비교는 각각 −1.12%, +0.20%였다. 두 번의 측정에서 이 장비의 8요청 처리량이 일관되게 향상됐다는 근거는 얻지 못했다. [이번 집계와 블록별 수치](portable-amd-recheck.json) · [앞선 AMD 캠페인](result-summary.md)

## 스케줄러별 처리량

절대값은 조건마다 6블록에서 측정한 생성 tok/s 평균이다. 변화율은 같은 블록에서 계산한 처리량 비율의 평균이다. 대괄호는 두 프롬프트 세트별로 층화한 paired bootstrap 95% 구간이고, 분수는 후보가 더 빨랐던 블록 수다.

| 부하 | 동시 요청 | 기본 Linux | `neutral` | `prefill-pcore` | 후보 / 기본 Linux | 후보 / `neutral` |
|---|---:|---:|---:|---:|---|---|
| 평상시 | 8 | 42.41 | 42.44 | 42.14 | −0.58% [−2.47, +0.50], 4/6 | −0.70% [−2.07, +0.66], 3/6 |
| 한 코어 25% 부하 | 8 | 35.55 | 35.35 | 35.32 | −0.63% [−1.96, +0.77], 2/6 | −0.10% [−0.51, +0.31], 3/6 |
| 평상시 | 1 | 16.95 | 17.13 | 17.26 | +1.84% [+0.46, +2.99], 5/6 | +0.82% [−0.37, +2.00], 4/6 |
| 한 코어 25% 부하 | 1 | 16.56 | 14.73 | 16.03 | −3.20% [−4.58, −1.40], 1/6 | +9.43% [+3.61, +13.86], 6/6 |

`neutral`과 `prefill-pcore` 모두 선택한 서버에만 커널 스케줄러를 적용했다. 이 Ryzen은 동종 코어 6개로 구성된다. 후보가 우선 배치할 P-core 목록은 비어 있었고, 커널에서 기록한 선택 시도와 성공은 각각 0회였다. 부하가 있는 단일 요청에서 나타난 `neutral` 대비 +9.43%를 P-core 우선 배치의 효과로 해석할 근거가 없다. 같은 조건에서 기본 Linux가 두 커널 구성보다 빨랐다.

### 8요청 응답 시간과 CPU 사용량

| 부하 | 스케줄러 | 512토큰 완료 시간(초) | 서버 CPU초 | 요청 기준 Prefill tok/s | 요청 기준 Decode tok/s |
|---|---|---:|---:|---:|---:|
| 평상시 | 기본 Linux | 12.08 | 72.28 | 29.68 | 9.00 |
| 평상시 | `prefill-pcore` | 12.15 | 72.73 | 29.31 | 8.98 |
| 한 코어 25% 부하 | 기본 Linux | 14.41 | 82.07 | 25.39 | 7.43 |
| 한 코어 25% 부하 | `prefill-pcore` | 14.50 | 77.28 | 25.12 | 7.40 |

`cpu25`에서 후보의 평균 서버 CPU 사용량은 5.83% 줄었고, 512토큰 완료 시간은 약 0.09초 늘었다. Prefill과 Decode는 각각 요청별 해당 토큰 수 합을 해당 시간 합으로 나눈 값이다. 동시 요청의 실행 시간은 서로 겹친다.

## 측정 조건과 검증

- 배치 실험은 커밋 `a7ec206`에서 새로 빌드한 CPU 전용 OpenMP 런타임, 같은 원본 GGUF, 같은 물리 코어 대표 CPU `0,2,4,6,8,10`을 사용했다. 생성 스레드 5개, 배치 스레드 6개, `unified-conservative`와 `fixed6`를 세 구성에 공통 적용했다. [측정 커밋](https://github.com/codinghuman0/llama-scheduler/commit/a7ec206f23c61441ed6478465d3e94f9e7f8d815)
- 매 방문마다 서버를 새로 시작하고, 서로 다른 요청 8개와 별도 단일 요청을 각각 워밍업 후 측정했다. 요청당 출력은 64토큰이다. 조건당 6가지 실행 순서를 한 번씩 사용했다. 총 36방문, 본 측정 72구간, 실제 생성 20,736토큰이었다. 원시 응답의 토큰 수와 HTTP 시작·종료 시각으로 72개 처리량과 모든 블록의 변화율을 다시 재현했다.
- 모든 블록에서 워밍업과 본 측정의 생성 토큰 ID가 세 구성 사이에 일치했다. 요청 간 프롬프트 캐시 재사용은 0이었다. 워밍업과 본 측정 구간 양 끝의 전원 기록 288개에서 AC가 연결돼 있었다. CPU 10에 건 부하의 본 측정 실소비량은 0.2494~0.2559코어였다.
- 24회의 커널 방문에서 서버 worker의 실제 `SCHED_EXT` 정책과 고정 CPU 범위를 확인했다. 커널 수신기가 상태 전환 336회와 idle 96회를 기록했고, 모니터 표본 968개에서 위반이 없었다. 모든 loader가 정상 종료됐고 최종 커널 상태는 `disabled`였다.

## 별도 혼합 요청 실험 `m4`

기본 Linux에서 같은 native 런타임의 `cap128`과 `head64`를 한 번씩 순서대로 실행했다. 동일한 128토큰 입력의 Decode 요청 4개가 진행되는 동안 6,144토큰 Prefill 요청 1개를 추가했다. 모든 요청에서 `cache_prompt=false`를 사용했고, 워밍업 5건과 본 측정 5건의 토큰 ID가 각각 일치했다.

| 본 측정 | `cap128` | `head64` | 변화 |
|---|---:|---:|---:|
| 520토큰 전체 생성 처리량 | 7.17 tok/s | 7.67 tok/s | +6.99% |
| 520토큰 완료 시간 | 72.52초 | 67.78초 | −6.53% |
| Decode 요청 4개 중 가장 큰 p95 토큰 간격 | 1,586 ms | 1,093 ms | −31.09% |

이 결과는 런타임의 혼합 요청 처리 방식을 비교한 1쌍이다. 반복 측정에 따른 불확실성과 순서 효과는 추정할 수 없다. 역사적 원본 B0와 통합 런타임의 성능 차이는 다른 프로파일과 요청당 128토큰을 쓴 두 캠페인에서 측정했다. 당시 8요청 처리량 개선은 평상시 +17.92~18.11%, `cpu25`에서 +32.88~37.43%였다. [B0 직접 비교 보고서](../amd-published-direct-v1/result-summary.md)

## 재현

저장소 루트에서 일반 계정으로 실행한다. `placement`는 선택된 서버 전용 loader에만 sudo를 사용한다. `m4`에는 sudo가 필요 없다. 원시 데이터 경로는 각 명령이 출력한다.

```bash
bash scripts/run-cpu-experiment.sh placement
bash scripts/run-cpu-experiment.sh m4
```

원래 측정 장비에서 이번 배치 결과를 다시 집계하는 명령은 다음과 같다.

```bash
cd new-a-workspace
python3 -B experiments/amd-prefill-placement-ac-v1/analyze.py \
  state/integration-v2/prefill-smoke-placement.fWtlTBKr/campaign
```
