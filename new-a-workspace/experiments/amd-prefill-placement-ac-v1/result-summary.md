# Ryzen 5 5500U에서 측정한 Prefill CPU 배치 정책

**AMD에서 `prefill-pcore`는 기본 Linux보다 일관되게 빠르지 않았다.** 8개 동시 요청에서 기본 Linux 대비 평균 paired 변화는 평상시 **−1.12%**, `cpu25`에서 **+0.20%**였고, 두 95% 구간 모두 0%를 포함했다. `cpu25`에서는 거의 같은 처리율로 서버 CPU 시간이 81.94초에서 76.42초로 줄었다. 단일 요청의 `cpu25` 처리율은 기본 Linux 대비 **−3.38%**였으며 95% 구간은 −6.80%~+0.20%였다.

### 전체 처리율

절대값은 각 조건에서 여섯 번 측정한 전체 생성 tok/s의 산술평균이다. 비교 열은 블록 단위 평균 변화율, 95% paired bootstrap 구간, 후보가 더 빨랐던 블록 수를 표시한다.

| 부하 | 요청 수 | Linux | `neutral` | `prefill-pcore` | 후보 / `neutral` | 후보 / Linux |
|---|---:|---:|---:|---:|---|---|
| 평상시 | 8 | 42.93 | 42.64 | 42.42 | −0.50% [−0.82, −0.22], 1/6 | −1.12% [−3.56, +0.23], 4/6 |
| `cpu25` | 8 | 35.66 | 35.34 | 35.73 | +1.11% [+0.22, +2.46], 5/6 | +0.20% [−0.99, +1.34], 3/6 |
| 평상시 | 1 | 17.05 | 17.20 | 17.13 | −0.43% [−2.26, +1.00], 4/6 | +0.45% [−0.17, +1.07], 3/6 |
| `cpu25` | 1 | 16.19 | 15.49 | 15.63 | +1.15% [−2.16, +4.57], 3/6 | −3.38% [−6.80, +0.20], 2/6 |

8개 요청에서 `prefill-pcore/neutral`의 방향은 배경 부하에 따라 뒤바뀌었다. 실제 AMD 커널에서 P-core 선택 시도와 성공은 전부 0회였다. 이 차이로 Intel의 Prefill P-core 배치 효과를 추정할 수 없다. `neutral/Linux`의 8요청 변화는 평상시 −0.63% [−2.74, +0.68], `cpu25`에서 −0.89% [−1.72, −0.06]였다. Linux와의 비교에는 선택 child 스케줄러와 Lite 계측 경로의 비용이 함께 들어간다. 평상시 첫 블록의 후보/Linux −7.41%도 집계에 포함했다.

### 실행 및 데이터 감사

- 36방문·72개 본 측정에서 20,736토큰을 생성했다. 모든 블록에서 세 구성의 프롬프트와 출력 토큰이 일치했다. 원시 응답과 monotonic 시각에서 독립적으로 재계산한 72개 처리율과 12개 대비의 paired 변화율이 결과 파일과 일치했다. [집계 결과](results.json)
- 24회의 Lite 스케줄러 방문에서 실제 worker의 정책 7과 고정 CPU mask를 확인했다. 커널 수신기는 총 336개 상태 전환과 96개 idle을 기록했다. 963회 모니터 샘플에서 guard 실패가 없었고, 모든 loader가 정상 종료·분리됐다.
- 모든 측정 창의 양 끝에서 AC 연결을 확인했다. `cpu25`의 본 측정 실소비량은 0.2500~0.2561코어였다. 배경 부하를 읽은 구간과 HTTP 구간 길이의 차이는 최대 3.83 ms였고, 72개 창 모두에서 스레드 신원이 유지됐다.
- 이 수치는 같은 통합 런타임에서 스케줄러만 바꾸는 한 번의 AMD 캠페인을 설명한다. 원본 llama.cpp와의 비교는 이전 캠페인에 별도로 기록돼 있다. [기존 원본 대비 측정](../amd-published-direct-v1/result-summary.md)

## 비교 조건

세 구성은 동일한 OpenMP 통합 런타임과 원본 GGUF를 사용했다. `linux`는 기본 Linux 스케줄러를 사용했다. `neutral`과 `prefill-pcore`는 서버와 그 worker에만 sched_ext를 적용하고 같은 weighted-vtime 큐, state-v2 수신기, Lite 계측을 사용했다. Ryzen 5 5500U의 물리 코어 여섯 개는 동종 코어다. 이 장비에서 `prefill-pcore`의 P-core 선호 목록은 비어 있다.

| 항목 | 설정 |
|---|---|
| 호스트 | AMD Ryzen 5 5500U, 6코어·12스레드, Linux `7.0.0-43-generic`, AC 전원 |
| 서버 자원 | 논리 CPU `0,2,4,6,8,10`, `--threads 5 --threads-batch 6 --threads-http 8`, CPU 추론 |
| 런타임 | `unified-conservative`, `fixed6`, 역할별 pool, state-v2, OpenMP |
| 요청 | 서로 다른 프롬프트 8개를 동시에 처리하는 두 cohort를 블록마다 교대. 각 방문에서 별도로 단일 요청도 측정 |
| 생성 설정 | 요청당 64토큰, 결정적 생성, 요청 간 캐시 재사용 0 |
| 부하 | 평상시와 CPU 10에 50 ms마다 CPU 시간 12.5 ms를 요구하는 `cpu25`. 부하 프로세스는 기본 Linux 정책 |
| 순서 | 조건마다 6블록. 매 블록에서 세 구성을 모두 실행하고 6가지 순열을 한 번씩 사용. 조건의 선후도 교대 |

무거운 계측은 별도의 FULL smoke에서 실행했다. 이때 두 옵션 모두 토큰이 일치했고, 각각 커널에서 상태 전환 14회와 idle 4회를 수신하고 정상 분리됐다. FULL은 실제 CPU의 실행 시작 횟수를 저장한다. 본 측정의 Lite는 정책 시도·성공과 안전 검사를 유지한다. [FULL smoke 원시 결과](pair-metrics.json)

## 지표의 정의

- **전체 처리율**은 한 HTTP cohort가 실제로 생성한 토큰 수를 cohort 전체 응답 시간으로 나눈 값이다. CPU초는 같은 구간에 서버 프로세스가 사용한 CPU 시간이다. 각 방문은 새 서버를 시작하고 8개 동시 요청과 단일 요청에 대해 차례로 워밍업 1회와 본 측정 1회를 수행한다. 모델 로딩과 워밍업은 집계에서 제외한다.
- **Prefill 및 Decode tok/s**는 요청별 해당 phase의 토큰 수 합을 요청별 해당 phase 시간 합으로 나눈 값이다. 동시 요청의 시간 구간은 서로 겹칠 수 있다.
- **변화율**은 동일 블록에서 `100 × (후보 처리율 / 대조군 처리율 − 1)`을 계산한 뒤 평균한다. 95% 구간은 cohort별로 블록을 복원 추출한 paired bootstrap 20,000회에서 계산한다. 동시 요청 8개는 한 번의 관측이다.
- AC는 워밍업과 본 측정 전후에 확인한다. `cpu25`는 별도 프로세스의 CPU tick과 affinity를 같은 HTTP 구간 양 끝에서 확인한다. 허용 범위는 한 코어의 0.22~0.28, 같은 블록의 세 구성 사이 최대 차이는 0.025코어다. 마이그레이션과 문맥 전환은 양 끝의 서버 스레드 신원이 일치하는 구간에서 집계한다.

## 재계산과 재실행

`new-a-workspace`에서 원본 측정 장비의 로컬 원시 응답·worker mask·커널 로그를 다시 감사할 수 있다. 공개 저장소에는 블록별 변화율을 포함한 집계 JSON과 짧은 커널 smoke 결과를 보관한다.

```bash
python3 -B experiments/amd-prefill-placement-ac-v1/analyze.py \
  state/integration-v2/amd-prefill-placement-ac-20261125-01
```

같은 AMD 장비에서 새 결과 디렉터리로 반복하는 명령이다. 일반 계정에서 실행하며, 개별 SCX 방문은 체크포인트가 지정한 제한시간·선택 child loader에 sudo를 사용한다. 처음 사용하는 체크아웃에서는 `bash scripts/prefill-pcore-smoke.sh prepare`로 이 실험이 확인하는 런타임과 스케줄러 번들을 빌드한다.

```bash
python3 -B experiments/amd-prefill-placement-ac-v1/measure.py run \
  "state/integration-v2/amd-prefill-placement-ac-$(date +%Y%m%dT%H%M%S)"
```
